# 04 · AI 协作开发复盘

> 这份文档记录的不是"我们做成了什么"，而是**我们怎么和 AI 一起做的，以及在哪里翻的车**。
>
> 大部分 AI 编码教程教你怎么写出更长的提示词。这份文档反过来——它记录的是**提示词写得再好也没用的那些时刻**。

---

## 0. 先说结论

一个学期、三个人、三端代码，全程用 AI 辅助（主要是对话式编码 + 让它读代码给方案）。回头看，AI 帮我们省掉的最大成本不是"写代码"，而是：

| 环节 | AI 的真实贡献 | 我们省了什么 |
|---|---|---|
| 需求整理 | 把散乱的想法整理成结构化文档 | 大概 3 天 |
| 架构设计 | 给出三端拆分方案和取舍对比 | 2 天 |
| 写页面 | 一个页面 20 分钟出可用版本 | 最多，约 60% 的编码量 |
| 找 bug | 贴报错就能定位 | 省了查文档的时间 |
| **写文档** | **基本全靠它** | 这是我们最不想自己写的东西 |

但代价也很真实：**AI 会"自信地改坏你已有的东西"，而且改完不告诉你改了哪里。**

下面四个案例，全部真实发生过。

---

## 1. 我们实际是怎么协作的

不是"提需求 → AI 写完 → 收工"。真实流程是这样：

```
① 我们先想清楚要什么（业务规则、状态、交互）
     ↓
② 让 AI 读现有代码，先说方案，不直接改
     ↓
③ 方案对了，让它改；一次只改一个模块
     ↓
④ 改完立刻在模拟器/浏览器里点一遍
     ↓
⑤ 发现不对，把现象（不是猜测）贴回去
```

第 ② 步是关键。如果直接说"帮我加一个优惠券页面"，AI 会自己编一套数据结构，跟后面的订单流程对不上。所以我们的固定句式是：

> "先读 `pages/orderCreate.vue` 和 `mock/index.js`，告诉我如果要加优惠券，需要动哪些文件、数据放哪。**先不要改。**"

这个"先不要改"救了我们很多次。

## 2. 四个真实翻车案例

### 案例一：快照把新写的代码"还原"没了

**发生什么**

某天晚上做完 4 个新页面（配送追踪、晒单广场、优惠券、收藏），第二天打开项目，发现：

- `uniapp/pages.json` 变回了旧版本，只剩 10 个页面
- `pages/` 下那 4 个新文件夹整个消失
- 但 `web/` 那边当天写的 3 个后台页面还在

**为什么**

项目里有个"可还原基线"的快照包（`城野随行_源码快照_2026-11-03.zip`），本来是为了"改坏了能回退"。有人在环境出问题时解压了这个快照覆盖回去，于是 `uniapp/` 被整体回滚到 11 月 3 日的状态。

**怎么救回来的**

这 4 个页面的代码已经不在磁盘上了，但**对话记录里还在**——每一次写文件的操作都被记在会话日志里。

做法：写了个 Python 脚本，读会话日志（`.jsonl` 格式，一分行一条记录），按时间顺序把 20 次「写文件」操作和 2 次「编辑」操作重放出来，还原到临时目录，打包成 tar.gz，再解压回项目。

```python
# 简化后的逻辑
import json, os

for line in open('trajectory.jsonl', encoding='utf-8'):
    rec = json.loads(line)
    if rec.get('type') == 'tool_use' and rec['name'] == 'Write':
        path = rec['input']['file_path']
        content = rec['input']['content']
        # 按原始路径写回
        os.makedirs(os.path.dirname(path), exist_ok=True)
        open(path, 'w', encoding='utf-8').write(content)
```

**这里踩的第二个坑**

Windows 上这台机器的 PATH 里**没有 `tar` 命令**（`tar --version` 报 not recognized）。所以打包和解压都绕开了 `tar`，用 Python 的 `tarfile` 模块：

```powershell
python -c "import tarfile; tarfile.open('restore.tar.gz').extractall('.')"
```

**学到什么**

1. 快照/版本回退是**双向刀**——它救你，也会杀你。回退前一定先确认"当前工作区有没有未提交的新东西"
2. **AI 协作开发的会话记录本身就是备份**。如果早一点知道这点，就不会有那两小时
3. 不要假设命令行工具齐全。Windows 上 `tar` 不一定有，`curl` 是老版本，`ls` 是别名

### 案例二：命令跑在错误的目录里

**发生什么**

```powershell
PS D:\...\软件工程> npm run dev
npm error code ENOENT
npm error path D:\...\软件工程\package.json
npm error enoent Could not read package.json
```

然后是：

```powershell
PS D:\...\软件工程\web> npm run dev
> vite
'vite' 不是内部或外部命令，也不是可运行的程序
```

**为什么**

两个不同的错误，我们一开始当成一个问题查：

| 报错 | 真实原因 |
|---|---|
| `ENOENT ... package.json` | 在**项目根目录**跑命令，但根目录没有 `package.json`（`uniapp/` 和 `web/` 各有自己的） |
| `'vite' 不是内部或外部命令` | 目录对了，但**没装依赖**，`node_modules/.bin/vite` 不存在 |

**为什么容易混**

因为项目是"一个根目录下装了两个独立工程"的结构：

```
软件工程/          ← 这里没有 package.json
├── uniapp/       ← 有自己的 package.json
└── web/          ← 有自己的 package.json
```

`cd` 到根目录跑 `npm run dev`，直觉上"我在项目里了"，实际上 npm 找不到任何东西。

**学到什么**

1. **报错先读第一行**。`ENOENT` 和 `'vite' 不是命令` 是两类问题（路径 vs 依赖），混在一起查会绕远
2. README 里必须写清楚"在哪个目录跑哪条命令"。我们后来在 [README](../README.md) 加了一张"常见启动报错"表，就是被这个坑逼出来的
3. `npm install` 和 `npm run dev` 是两步，不能只做一步

### 案例三：讲法和界面打架

这个案例最能说明 AI 协作的真实风险。

**发生什么**

答辩前演练，被问："配送中可以取消订单吗？"

我们答得很顺："技术上任意状态都能转已取消，业务上按状态分级扣费——配送中扣配送费约 20%，布置中扣已发生费用约 50%。"

对方追问："那为什么小程序里没写这个说明？"

去看代码，`pages/orderDetail.vue` 的 `onCancel()` 当时只有一句通用文案：

```js
content: '确定取消该订单吗？取消后不可恢复。'
```

确实没写。

**第一反应：补上**

于是让 AI 按状态生成四种文案：

```js
onCancel() {
  const status = this.order.orderStatus;
  let content = '确定取消该订单吗？取消后不可恢复。';
  if (status === '待支付') content = '订单尚未支付，取消后订单关闭，无需退款。…';
  else if (status === '已支付') content = '订单已付款但尚未派车，取消后全额退款。…';
  else if (status === '配送中') content = '装备已装车出发，取消将扣除配送费（约订单金额的 20%）。…';
  else if (status === '布置中') content = '装备已到场布置，取消将扣除已发生的人工与物料费用（约 50%）。…';
  // ...
}
```

看起来完美——讲法和界面终于一致了。

**但是错了**

再往下看，取消按钮的显示条件是：

```js
canCancel() {
  return this.order && this.order.orderStatus === '待支付';
}
```

**只有"待支付"才显示取消按钮。** 上面新加的"配送中扣 20%"、"布置中扣 50%"两段文案，**永远不会被执行到**。

再去看云函数，真相更清楚：

```js
// cloudfunctions/order/index.js:335
if (['待支付', '已支付'].indexOf(order.orderStatus) === -1) {
  return fail(CODE.ORDER_STATUS_INVALID, '仅待支付/已支付订单可取消');
}
```

**后端压根不允许配送中取消。** 我们答辩时讲的"配送中扣 20%"，是一个从来没实现过的规则——它是设计阶段的设想，被我们当成既成事实讲了出去。

**正确的处理**

不是把按钮放开（那样后端会直接拒绝，界面更穿帮），而是：

1. 承认现状：C 端只开放"待支付取消"和"已支付退款"，配送中及之后需人工处理
2. 那两段死代码**保留**，作为"业务规则想这么做但没实现"的痕迹
3. 在 [02 · 业务规则](02-business-rules.md#13-一个必须说清楚的点配送中不能取消) 里把这个边界写明

**学到什么（这是最重要的一条）**

> **AI 会认真执行你的每一个指令，但它不会告诉你这个指令和别处的代码矛盾。**

我们说"帮我按状态补文案"，它就老老实实补了四段，而且补得很合理。它不知道（也不会主动去查）`canCancel` 只放行一种状态。

所以：

- **改 UI 文案前，先看这个 UI 会不会出现**
- **改前端规则前，先看后端允不允许**
- **凡是"讲法"和"代码"不一致，以代码为准，然后决定改哪边**

这个坑我们后来做了一次专门的自查：把答辩手册里每一句业务口径，逐条翻到代码验证。查出来的不止这一处。

### 案例四：一个改动，两个副本

**发生什么**

加完优惠券和积分功能后，C 端能正常下单、用券、抵现。但切到 Web 后台，优惠券列表是空的。

**为什么**

因为 **Mock 数据有两份**：

- `uniapp/mock/index.js` —— 小程序用
- `web/src/utils/mock.js` —— 后台用

我们只在 C 端那份加了 `coupons` 种子和 `coupon.list` 分支，Web 那份没动。

同样的问题还有第三份：`mock-data/cloud-import/*.json`（部署到云数据库用）。

**改一次要改三处**，这是这个架构的固有成本（原因见 [03 · 数据模型](03-data-model.md#4-同一个数据存在三个地方)）。

**学到什么**

1. **AI 不会主动帮你同步副本**。你让它改 A，它就只改 A。除非你明确说"这个数据在 B 和 C 也有一份，一起改"
2. 所以每次改种子数据，我们的固定动作是：改完一处，立刻 `grep` 搜索同一个 ID（比如 `CP_NEW20`）在几个文件里出现
3. 长期解法是做一个共享 seed 生成脚本，让三处从一个源生成——这件事我们没做完，写在 [06 · 验收清单](06-acceptance.md) 的"未做"里

## 3. 从翻车里提炼的五条规则

不是"最佳实践"那种漂亮话，是我们真的贴在项目 README 里的东西。

### 规则一：先读再改

```
❌ "帮我加一个优惠券功能"
✅ "先读 pages/orderCreate.vue 和 mock/index.js，
    告诉我需要改哪些文件，数据放哪。先不要改。"
```

原因：AI 不了解你的项目结构时，会自己发明一套。让它先读，方案才落在真实代码上。

### 规则二：一次只改一个模块

同时让它改"页面 + Mock + 服务层 + 路由"，出问题时你不知道是哪一层的错。

### 规则三：报现象，不报猜测

```
❌ "请求失败了，你修一下"
✅ "点提交后弹窗显示 '订单未满 300 元，券不可用'，
    但订单金额是 399。传的 couponId 是 CP_FULL50。"
```

猜测会把你带偏，现象不会。

### 规则四：改完立刻验证，别攒着

AI 一次改 5 个文件，其中 1 个改错，你隔两天才发现——那时候你已经忘了当时在做什么。

### 规则五：涉及"同一份数据多处存在"时，明确告诉它有几处

```
✅ "CP_NEW20 这个券在 uniapp/mock/seed.js、
    web/src/utils/mock.js、mock-data/cloud-import/packages.json
    三个地方都有，一起改。"
```

## 4. AI 擅长什么、不擅长什么

一个学期的体感，很主观但很真实：

| 任务 | AI 表现 | 说明 |
|---|---|---|
| 写 CRUD 页面 | ⭐⭐⭐⭐⭐ | 表单、列表、分页，模板性极强，几乎一次就对 |
| 写样式 | ⭐⭐⭐⭐ | 布局能对，细节配色要调 |
| 生成 Mock 数据 | ⭐⭐⭐⭐⭐ | 造 10 条订单、3 个套餐，比手写快得多 |
| 写文档 | ⭐⭐⭐⭐⭐ | 这是它最强的地方，我们从需求文档到这份复盘全靠它 |
| 定位报错 | ⭐⭐⭐⭐ | 贴完整报错基本能定位，但偶尔会猜错方向 |
| **跨模块一致性** | ⭐⭐ | **最容易出错**，改了 A 不知道 B 也要改 |
| **业务规则合理性** | ⭐⭐ | 它能实现你写的规则，但不会告诉你规则本身有问题 |
| **判断"这个功能值不值得做"** | ⭐ | 完全不行，这是人的活 |

最后两行是这份文档存在的原因。

## 5. 如果重来一遍

### 会保留的

- **先方案后代码**的协作方式——这个流程本身是对的
- Mock 优先——让我们在没有云环境的情况下跑完了全流程
- 一个开关切 Mock/真实——答辩演示零风险

### 会改的

| 问题 | 重来怎么做 |
|---|---|
| 三份种子数据 | 做一个 `seed.json` 单一源，脚本生成三处 |
| 快照回退没有保护 | 回退前先 `git status`，或者干脆一开始就 `git init` |
| 讲法和代码不一致 | 答辩前做一次"口径 ↔ 代码"逐条核对（我们后来补做了） |
| 两个 `mock` 文件手动同步 | 至少写个 `check-mock-sync.js`，CI 里跑一下对比关键 ID 是否存在 |

### 最想早做的一件事

**第一天就 `git init`。**

我们整个项目没有版本控制，出了问题只能靠快照和会话日志救。如果一开始就有 git，案例一那两小时可以省掉，案例三那种"改了哪里"的困惑也不会有。

---

## 6. 一句话总结

> AI 让"做出来"变便宜了，但让"做对"没变便宜。
>
> 它能帮你把 100 行代码写完，但不能替你想清楚——**这 100 行该不该存在**。
