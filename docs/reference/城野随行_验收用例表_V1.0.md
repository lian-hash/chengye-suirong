## 附录 A：Web 管理后台静态托管说明

> 适用：需要把 Web 后台发布成**在线链接**（而非本机 `npm run dev`）时使用。uniCloud 提供「前端网页托管」，静态站点可直接托管在空间内。

### A.1 构建前必做（最容易踩坑）

- [ ] Web 后台的接口地址是在**构建时**由 Vite 静态注入的（`web/src/config/backend.js` 读 `VITE_*`），因此必须**先配置再构建**：
      ```bash
      # web/.env.production（或 .env）中写真实地址
      VITE_FORCE_MOCK=false
      VITE_UNICLOUD_HTTP_BASE=https://<你的空间域名>/http/
      ```
- [ ] `.env.production` 会随 `npm run build` 生效；改完环境变量**不需要**重启 dev-server，但**必须重新构建**。

### A.2 构建

```bash
cd 城野随行/web
npm install          # 首次
npm run build        # 产物输出到 web/dist
```

- [ ] 构建无报错，`web/dist` 下生成 `index.html` 与 `assets/`。
- [ ] 本地预览： `npm run preview`，确认页面能打开、能登录（此时走的是真实后端）。

### A.3 上传到 uniCloud 前端网页托管

- [ ] uniCloud 控制台 → 选择空间 `your-uni-cloud-space-id` → `前端网页托管`。
- [ ] 若首次使用，点击开通（免费额度足够课程设计使用），等待文件空间初始化完成。
- [ ] 上传 `web/dist` 下的**全部内容**（注意是 dist **目录内的**文件，`index.html` 应在根目录层级）。
- [ ] 记录托管给出的默认域名（形如 `https://xxx.static-xxx.com`），这就是 Web 后台的在线访问地址。

### A.4 SPA 路由注意（重要）

本项目使用的是 `createWebHistory()`（HTML5 History 模式，无 `#`），直接访问 `/order/list` 这类子路径时，静态托管若不做回退会把请求当资源查找并返回 404：

- [ ] **做法一（不改代码，推荐）**：在托管配置中设置「缺失路径重写到 `index.html`」（若控制台提供「重定向/回退规则」则配置 `/* → /index.html`，状态码 200）。
- [ ] **做法二（改一处代码即可）**：把 `web/src/router/index.js` 的 `createWebHistory()` 改为 `createWebHashHistory()`，重新构建上传 —— 路径变为 `#/order/list`，任意静态托管都能直接刷新。
- [ ] 验收：浏览器打开托管域名 → 登录后**手动刷新当前页**，不出现 404 即通过。

### A.5 与在线站点相关的补充检查

- [ ] 在线站点登录后能正常调用所有已开 URL 化的云函数（`webLogin / user / packageSite / order / delivery / equipment / finance / log`）。
- [ ] `initDB` **不要**长期挂在 URL 化上：演示/交付前关闭，或保留 `ADMIN_KEY`（详见操作单 §6.1）。
- [ ] 在线演示的地址、账号（`admin/admin123`）只发给需要演示的人；`.env`、密钥不要在录屏/截图中暴露。

### 10.3 发现的问题（Mock 逻辑 / 契约不符，仅报告，未修改）

- **F1（角色 / 鉴权缺失）·影响 P1-02 / P1-04 / P3-11(ent) / P6-02**：Web Mock 的 `mockHandle` 不在接口内做角色 / 权限校验，`webLogin.login` 也不校验密码。因此密码错误、B 端越权访问、财务越权、ent 退款均返回 `code=0` 而非契约的"非 0 / 4004"。这属于离线 stub 的**预期简化**（真实后端负责鉴权），但意味着这 4 条用例在 Mock 下无法验证"拒绝"分支。建议：若希望 Mock 也能演示越权拦截，可在 `mockHandle` 内按 `data._operator/_role` 增加轻量角色判定（不影响真实后端）。
- **F2（下架套餐详情未拦截）·影响 P2-02**：C 端 `packageSite.getPackage` 仅判断"套餐是否存在"，未判断 `onShelf`。下架套餐 PKG003 仍返回 `code=0` 与详情（契约期望 `4003`）。`listPackages` 已正确过滤上架，建议 `getPackage` 与之一致。
- **F3（缺 4001 参数校验）·影响 P3-05**：C 端 `order.create` 只做套餐/日期/场地/容量/装备的业务校验（失败返回 4003），未做必填字段与手机号格式（`1\d{10}`）的 `4001` 参数校验；缺 `siteId` 时返回 4003"场地不可用"而非 4001。真实后端有参数校验层，Mock 缺失。
- **F4（重复支付状态码取舍）·影响 P3-07**：C 端 `order.pay` 对已支付订单返回 `4009`（重复操作），验收表期望 `4002`（订单状态不允许支付）。两者均为"非成功"，语义上 4009 更贴切，但与验收契约不一致，建议对齐（或更新验收表说明）。
- **F5（退款状态值 / 库存）·影响 P3-11**：Web `order.refund` 退款后把 `orderStatus` 置为 `已退款`，而验收契约写的是 `已取消`；且退款未回加装备库存。
- **F6（库存联动时机差异）·影响 P3-01 / P3-09 / P5-04**：Mock 采用"派送扣减、回收归还"的**配送期联动**模型；而验收契约（对应真实后端）要求"下单预占、取消回加"的**下单期联动**。因此 `create` 不预占、`cancel` 不回加，P5-04 的"下单递减 / 取消回加"在 Mock 下不成立。建议：若要让 Mock 也更贴近契约，可在 `create` 预占、`cancel` 回加（与 `dispatch/recover` 不冲突，需按状态区分）。
- **F7（配送状态机断裂）·影响 P4-03（严重）**：Web Mock 的 `ADVANCE` 仅有 `dispatch(已支付→配送中)`、`setup(配送中→布置中)`、`recover(使用中→已完成)`，**缺 `布置中→使用中` 迁移且根本没有"已回收"状态**。结果：订单到达 `布置中` 后无法继续推进，回收操作对布置中订单返回 `4002`，7 态闭环在 Mock 中无法走到"已完成"。这是会**影响离线演示**的真实 Mock 逻辑缺口，建议补齐 `布置中→使用中` 与 `已回收` 中间态（或把 `recover` 的 `from` 放宽为 `布置中/使用中` 并经 `已回收` 落到 `已完成`）。
