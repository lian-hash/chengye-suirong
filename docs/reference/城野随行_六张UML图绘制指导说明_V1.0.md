# 图一、上下文模型图（系统边界图）

一、任务背景

城野随行平台需划定系统内外边界，识别全部外部参与者（人参与者与外部系统参与者），并明确系统与每个外部实体之间交互的数据流，为后续面向对象建模确定范围。

二、系统核心需求

1. 系统应区分 C 端用户、B 端运营人员、系统管理员三类人参与者；
2. 系统应通过微信开放平台完成授权登录，换取 openid；
3. 系统应通过微信支付（模拟）完成支付，获取支付回执；
4. 系统应向 C 端用户提供套餐/场地浏览、下单、支付、查询、评价、退款服务；
5. 系统应向 B 端运营提供套餐/场地/装备维护、配送调度、批量下单、统计服务；
6. 系统应向管理员提供权限管理、日志审计、全局统计服务；
7. 系统与微信开放平台交互的数据流为"授权 code / openid"；
8. 系统与微信支付交互的数据流为"支付请求 / 模拟回执"；
9. 系统与 C 端用户交互的数据流含"订单数据 / 支付结果 / 评价退款结果"；
10. 系统与运营/管理员交互的数据流含"维护数据 / 调度指令 / 统计报表 / 审计数据"。

三、绘制提示

1. 边界框识别：中央画"城野随行平台"大矩形方框（目标系统），四周排布外部参与者，系统外不画任何内部模块；
2. 参与者标注：人参与者用"小人"图标并标名称，外部系统用方框并标名称（微信开放平台、微信支付），区分人/系统两类；
3. 数据流标注：每条连线标注交互的数据流名称（如"授权 code""openid""支付请求""模拟回执""订单数据"），箭头表示数据流向；
4. 符号规范：系统边界为单一大矩形，外部参与者一律在框外，连线不得穿越系统方框，图面不画任何内部控制逻辑。

# 图二、用例图

一、任务背景

基于城野随行核心需求，按 UML 用例图标准绘制，覆盖全部参与者与用例，并准确表达参与者/用例之间、用例与用例之间的 <<include>>、<<extend>>、泛化关系。

二、系统核心需求

1. 游客可浏览套餐与场地；
2. 已登录用户可下单、模拟支付、查询订单、评价、取消/退款；
3. 运营可维护套餐/场地/装备、执行配送调度、批量下单、查看统计；
4. 管理员可管理权限、检索日志、查看全局统计；
5. 下单前须先校验（套餐上架/周期/容量/库存）——校验为下单的包含用例；
6. 下单后须支付——支付为下单的包含用例；
7. 订单评价可由取消/退款扩展；
8. 微信授权登录为下单的前置包含用例；
9. 游客与已登录用户存在泛化（已登录用户继承游客的浏览能力）。

三、绘制提示

1. 执行者识别：人参与者=游客、已登录用户、运营人员、管理员；外部系统=微信开放平台、微信支付；明确区分人与系统；
2. 用例覆盖：将每条核心需求映射到至少 1 个用例，确保无需求遗漏（如"多条件搜索套餐""支付""应用支付方式"等）；
3. 关系标注：<<include>> 由基用例指向子用例（下单 → 校验 / 支付 → 应用支付方式）；<<extend>> 由扩展用例指向基用例（取消/退款 → 评价）；泛化用空心三角（已登录用户 ──▷ 游客）；
4. 符号规范：参与者名简洁（用"取消预订"而非"用户取消订单"）；<<include>>/<<extend>> 构造型箭头方向必须正确，用例用椭圆、参与者用小人。

# 图三、活动图（带泳道）

一、任务背景

为清晰呈现城野随行"下单—支付—配送—布置—使用—回收—完成"的端到端业务流，需绘制带泳道（分区）的活动图，区分 C 端用户、系统、运营人员三类职责，并体现校验/支付的分支与汇合。

二、系统核心需求

1. 用户选择套餐与场地并提交预约；
2. 系统执行四重校验（套餐上架 / 可预约周期 / 场地容量 / 装备库存）；
3. 校验通过则生成订单并锁库存，否则提示原因并终止；
4. 用户发起模拟支付，成功则订单置"已支付"；
5. 系统创建配送任务并派单；
6. 运营现场布置、用户使用、运营回收；
7. 订单确认完成；任意态可取消/退款。

三、绘制提示

1. 泳道划分：自顶向下（或自左向右）设"C 端用户""系统""运营人员"三条泳道，活动归入对应泳道；
2. 节点类型：初始节点（实心圆）、活动节点（圆角矩形，写"动词+宾语"）、分支（菱形，标监护如"校验通过？"）、汇合、终止节点（牛眼）；
3. 分支与汇合：校验不通过走异常分支回到提示/终止；支付失败可重试后汇合到"已支付"；取消/退款分支指向"已取消"终止；
4. 符号规范：每个分支必须有进有出、汇合对齐，终止节点可为"已完成"与"已取消"两个，活动节点不写判断逻辑。

# 图四、类图

一、任务背景

为表达城野随行平台的静态结构，需绘制 UML 类图，识别实体类、边界类、控制类，并刻画它们之间的关联、聚合、组合、依赖与泛化关系，标注关联多重度。

二、系统核心需求

1. 识别实体类 User / Site / Package / Order / OrderItem / Equipment / DeliveryTask，每类给出属性与主要操作；
2. 识别边界类 MiniProgramView / WebAdminView（对应人机界面）；
3. 识别控制类 *Service（封装业务规则）；
4. User 1——* Order 关联、Order 1——* OrderItem 组合、Package 聚合 * Equipment、Order *——1 Site / Package 关联；
5. 控制类依赖实体类与边界类；标注各关联端多重度（1、*、0..1 等）。

三、绘制提示

1. 类识别：实体类对应持久化对象，边界类对应界面，控制类对应业务规则/流程，三类用同一矩形但可在名称区注明版型（<<entity>>/<<boundary>>/<<control>>）；
2. 属性与操作：每类写"类名 / 属性（含类型）/ 主要操作"，如 Order{orderId,status,amount} 操作 create()/pay()/cancel()；
3. 关系绘制：关联=实线、聚合=空心菱形在整体端、组合=实心菱形在整体端、泛化=空心三角、依赖=虚线箭头（由使用方指向被使用方）；
4. 符号规范：多重度标在关联两端（如 User 端 1、Order 端 *），组合菱形在 Order 端（整体），依赖箭头方向正确，避免遗漏关键关系；
5. 角色表达：游客与已登录用户不单列子类，统一由 User 的属性 role: Enum{guest,user} 区分（完整取值域 guest/user/operator/admin，见数据字典 A03），既简化图面又避免为两个空子类多画两个类框；
6. 布局约定（本项目统一要求）：采用 6 列 × 4 行网格，控制类与它所主管的实体类放在同一列，依赖画成短竖线；跨列的长连线一律走预留通道（上方空白带、左右空白纵巷、泳道间空白横巷），**任何连线都不得穿过任何一个类框**，两条相邻平行线间距不小于 20 像素。六张图均已通过几何自检脚本 `drawio/check_oop_geom.py` 验证：连线穿框数 0、类框重叠数 0。

# 图五、时序图

一、任务背景

为表达"创建订单"场景的对象间动态协作，需绘制 UML 时序图，按时间顺序展示参与者、各对象生命线与消息调用，且消息名称须与类图中类的操作方法一致。

二、系统核心需求

1. 用户经 :MiniProgramView 提交订单；
2. :OrderController 接收并转 :OrderService.create(预约信息)；
3. :OrderService 调用 :Package.isOnShelf()/checkPeriod()、:Site.queryAvailable()、:Equipment.checkStock() 完成四重校验；
4. 校验通过 :Order.create() 生成订单、锁库存；
5. :Order.pay() 触发模拟支付；
6. :DeliveryService.dispatch() 创建配送任务；
7. 返回订单号与待支付状态给界面。

三、绘制提示

1. 对象识别：顶部画参与者(:MiniProgramView)与各对象(:OrderController/:OrderService/:Package/:Site/:Equipment/:Order/:DeliveryService)，每个对象向下拉垂直虚线生命线；
2. 消息对应类图：消息名必须与类图操作方法一致（create/isOnShelf/checkPeriod/queryAvailable/checkStock/pay/dispatch 等）；
3. 激活条：对象执行方法期间画细长方块（激活条），方法结束收回；
4. 符号规范：消息箭头自上而下、返回消息用虚线箭头，严格按时间顺序，生命线不交叉，避免消息名与类图不符。

# 图六、状态图

一、任务背景

为表达订单对象的生命周期，需以 Order 为状态机主体绘制 UML 状态图，完整列出其所有可能状态，并标注触发迁移的事件与监护条件。

二、系统核心需求

1. 订单初始为"待支付"；
2. 支付成功 → "已支付"；
3. 派单 → "配送中" → 布置 → "布置中" → 使用 → "使用中" → 回收 → "已回收" → 确认 → "已完成"；
4. 任意态（除终态）可经取消/退款 → "已取消"；
5. "已完成""已取消"为终态，不再迁移。

三、绘制提示

1. 对象选择：以 Order 单一对象为状态机主体，不混入其他对象；
2. 状态列举：完整画出 7 个主状态（待支付/已支付/配送中/布置中/使用中/已回收/已完成）+ 2 个终态（已完成/已取消），避免遗漏；
3. 迁移标注：每条迁移标"触发事件[监护条件]"（如 pay()[支付回执有效]、dispatch()、arrange()、useStart()、recycle()、confirm()、cancel()/refund()）；
4. 符号规范：初始=实心圆、终止=牛眼、状态=圆角矩形、迁移=箭头+事件[监护]，监护条件可省略时亦须保证事件清晰。
