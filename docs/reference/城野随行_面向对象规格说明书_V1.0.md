# 1 引言

## 1.1 项目背景


描述现实业务存在什么问题、为什么要开发本系统：

城野随行是一个面向城市微露营（city 微露营）场景的一站式配送与履约平台。现实业务中，城市周边露营需求快速增长，但用户自行采购、搬运帐篷与装备、寻找合规场地等环节繁琐，运营方也缺乏一套系统化的套餐发布、订单履约与装备调度手段。

说明系统要解决的业务痛点：

- 用户端：露营装备与场地套餐信息不对称、下单与支付链路分散、履约进度不透明；
- 运营端：套餐与场地人工维护易错、订单状态靠口头/表格跟踪、装备库存与消杀无系统记录；
- 管理端：营收、退款、套餐热度缺乏统一统计，操作无审计留痕。

列出本系统需要对接哪些上下游外部业务/外部系统：

- 微信开放平台（提供用户授权登录，换取 openid）；
- 微信支付（本环境采用"模拟支付"通道，用于教学演示支付闭环）；
- DCloud uniCloud 云数据库 / 云存储（作为平台自身的数据与文件底座，非外部对接方）。

## 1.3 范围

### 1.3.1 功能范围


列出系统包含的全部核心功能：

- P1 用户服务：微信授权登录、角色识别与权限加载、个人中心与信息维护；
- P2 套餐与场地：套餐浏览与查询、套餐详情与场地选择、套餐信息维护、场地信息维护；
- P3 订单服务：订单创建、模拟支付、订单查询与状态跟踪、订单评价、订单取消与退款、批量下单（B 端）；
- P4 配送调度：配送执行、现场布置、回收处理、配送记录管理；
- P5 装备管理：装备信息维护、装备出入库、消杀登记、低库存预警；
- P6 财务与日志：营收统计、退款统计、热门套餐排行、对账单导出、操作日志检索。

明确写出系统不实现哪些功能，划定功能边界：

- 真实在线支付与第三方资金清结算（仅模拟支付）；
- 真实地图导航与路径规划（仅记录配送地址与状态）；
- 装备的实体生产/采购供应链；
- 与景区票务、酒店住宿等跨行业系统的打通。

### 1.3.2 业务范围


列出系统覆盖的全部用户角色：

- C 端用户（微信小程序）：浏览、下单、支付、查询、评价、取消/退款；
- B 端运营人员（Web 后台）：套餐/场地/装备维护、配送调度、批量下单、统计对账；
- 系统管理员（Web 后台）：角色与权限、日志审计、全局统计。

列出系统覆盖哪些业务流程，哪些业务流程不在系统处理范围内：

- 覆盖：套餐发布 → 用户下单 →（模拟）支付 → 配送 → 现场布置 → 使用中 → 回收 → 完成；以及评价、退款、装备出入库与消杀、财务统计。
- 不覆盖：真实物流运输、线下现金收款、第三方营销投放。

# 2 总体描述

## 2.1 功能概述


城野随行平台为城市微露营提供"套餐浏览—下单支付—配送布置—使用回收—财务对账"的端到端线上闭环。C 端用户通过微信小程序完成浏览与下单，B 端运营在 Web 后台进行套餐/场地/装备维护与配送调度，系统管理员负责权限与审计；平台以订单为中心串联各业务模块，并对装备库存与履约状态做全程跟踪。

## 2.2 用户特征


| 角色名称 | 在系统中的工作职责 | 计算机操作技术能力 |
| --- | --- | --- |
| C 端用户 | 浏览套餐与场地、下单、模拟支付、查询订单状态、评价、申请取消/退款 | 熟悉微信小程序操作，无专业开发能力 |
| B 端运营人员 | 维护套餐/场地/装备信息、执行配送与布置、批量下单、查看统计与对账 | 具备日常办公软件与 Web 后台操作能力 |
| 系统管理员 | 角色权限管理、操作日志审计、全局营收/退款统计 | 具备系统后台管理能力，了解基本权限模型 |

## 2.3 运行环境


硬件环境：分别写服务器硬件配置、客户端硬件设备要求：

- 服务器（云）：DCloud uniCloud 云函数实例 + 云数据库 + 云存储（由平台托管，无需自管物理机）；单实例建议 ≥ 1 核 2G 等效算力。
- 客户端：C 端为手机（iOS / Android 微信客户端）；B 端/管理端为带浏览器的 PC（推荐 Chrome / Edge）。

软件环境：服务器操作系统、数据库、后端框架/中间件；客户端软件环境：

- 服务器：DCloud uniCloud（Node.js 云函数运行时、MongoDB 兼容文档数据库、对象存储）。
- 客户端框架：C 端 uni-app（Vue3 语法）编译为微信小程序；B 端/管理端 Vue3 + Element Plus Web 应用。
- 数据库：uniCloud 云数据库（文档型，兼容 MongoDB 查询语义）。

### 3.1.2 用例模型（用例图 + 用例规约）


文字说明识别出来的所有参与者：

- 游客（未登录 C 端）：仅可浏览；
- 已登录用户（C 端）：下单、支付、查询、评价、取消/退款；
- 运营人员（B 端）：维护套餐/场地/装备、配送调度、批量下单、统计；
- 管理员：权限管理、日志审计、全局统计；
- 外部系统参与者：微信开放平台（<<include>> 授权登录）、微信支付（<<include>> 模拟支付）。

对每一个关键用例，编写用例规约，规约必须包含：用例名称、参与者、前置条件、正常执行流、替代/异常流、后置条件。

用例规约（节选关键用例）：

- 用例 UC-01 创建订单：参与者=已登录用户；前置条件=用户已登录且套餐上架、预约周期/场地容量/装备库存均满足；正常流=①选套餐与场地填预约信息 ②四重校验通过 ③生成订单锁库存 ④返回订单号与待支付 ⑤触发模拟支付；异常流=A1 校验失败提示原因终止、A2 并发超卖回滚；后置条件=订单进入"待支付"，容量与库存被锁定。
- 用例 UC-02 模拟支付：参与者=已登录用户、微信支付（模拟）；前置条件=存在"待支付"订单；正常流=①发起支付 ②调模拟支付通道 ③返回成功 ④订单置"已支付"并创建配送任务；异常流=A1 超时/失败保持待支付可重试；后置条件=订单"已支付"，生成配送任务。
- 用例 UC-03 批量下单（B 端）：参与者=运营人员；前置条件=运营已登录且多笔预约齐备；正常流=①录入多笔预约 ②逐笔执行与 UC-01 相同校验与事务 ③批量返回订单号；后置条件=多笔订单均进入"待支付"。

一、任务背景

为清晰呈现城野随行"下单—支付—配送—布置—使用—回收—完成"的端到端业务流，需绘制带泳道（分区）的活动图，区分 C 端用户、系统、运营人员三类职责，并体现校验/支付的分支与汇合。

二、系统核心需求

1. 用户选择套餐与场地并提交预约；
2. 系统执行四重校验（套餐上架 / 可预约周期 / 场地容量 / 装备库存）；
3. 校验通过则生成订单并锁库存，否则提示原因并终止；
4. 用户发起模拟支付，成功则订单置"已支付"；
5. 系统创建配送任务并派单；
6. 运营现场布置、用户使用、运营回收；
7. 订单确认完成；任意态可取消/退款。

三、绘制提示

1. 泳道划分：自顶向下（或自左向右）设"C 端用户""系统""运营人员"三条泳道，活动归入对应泳道；
2. 节点类型：初始节点（实心圆）、活动节点（圆角矩形，写"动词+宾语"）、分支（菱形，标监护如"校验通过？"）、汇合、终止节点（牛眼）；
3. 分支与汇合：校验不通过走异常分支回到提示/终止；支付失败可重试后汇合到"已支付"；取消/退款分支指向"已取消"终止；
4. 符号规范：每个分支必须有进有出、汇合对齐，终止节点可为"已完成"与"已取消"两个，活动节点不写判断逻辑。

## 3.2 非功能需求

### 3.2.1 性能需求


- 接口响应时间：常规查询/下单接口 P95 ≤ 500ms；统计类接口 ≤ 2s。
- 并发用户数量：支持 ≥ 500 并发在线用户；下单峰值 ≥ 100 TPS。
- 定时/批量：批量下单单批 ≤ 200 条，处理时间 ≤ 10s；低库存预警每日定时扫描一次。
- 吞吐量：云函数按量弹性，单实例建议承载 ≥ 50 QPS。

### 3.2.2 安全需求


- 权限控制：基于角色（user/operator/admin）的访问控制，敏感操作（退款、日志检索、权限配置）须鉴权。
- 密码/凭证处理：微信 openid 不直接暴露；云函数调用须校验会话与角色。
- 操作日志：退款、权限变更、对账导出等敏感操作必须写入操作日志（D8 审计存储）。
- 数据传输安全：客户端与 uniCloud 之间走 HTTPS；云函数间调用使用平台内部鉴权。

### 3.2.3 可靠性需求


- 系统可用率：≥ 99.9%（依赖 uniCloud SLA）。
- 数据备份：云数据库每日自动备份，保留 ≥ 7 天；云存储多副本。
- 故障恢复：云函数无状态、可水平扩容；订单状态机保证履约不丢状态，异常可重试/回滚。
