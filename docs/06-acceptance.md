# 06 · 验收清单

> 这份文档的作用：**任何人在 20 分钟内，能自己判断这个项目到底跑不跑得起来、哪些是真的、哪些是占位的。**

## 1. 验收前提

不需要云环境，全部走 Mock：

```bash
# 终端 1：C 端
cd uniapp && npm install && npm run dev:mp-weixin

# 终端 2：Web 端
cd web && npm install && npm run dev
```

- 微信开发者工具导入 `uniapp/dist/dev/mp-weixin`
- 浏览器打开 `http://localhost:5173/`，账号 `admin` / 密码任意

## 5. 已知限制（逐条）

| # | 限制 | 影响 | 是否会在答辩/演示中暴露 |
|---|---|---|---|
| 1 | 支付是模拟的 | 没有真实扣款 | 不会，演示只说"模拟支付" |
| 2 | 地图是占位 | 没有真实定位和导航 | 可能会，被问"这是真的地图吗"时如实说 |
| 3 | 客服是静态弹窗 | 不能真的联系到人 | 不会 |
| 4 | 云函数未部署 | 无法验证真实链路 | **可能会**，被问"后端跑起来了吗"要如实说没有 |
| 5 | 数据不持久 | 刷新回到初始状态 | 不会，但要主动说明 |
| 6 | 无鉴权体系 | Mock 登录不校验真实身份 | 可能会，被问"安全怎么做"要讲设计方案 |
| 7 | 三份种子数据 | 改一处漏两处会不一致 | 不会，但自己要记住 |
| 8 | 无自动化测试 | 全靠手点 | 可能会，被问"怎么保证质量"要如实说 |

**这张表建议背下来。** 被问到时主动说"这个我们没做，原因是……"，比被问出来再解释要好得多。

## 6. 成熟度自评

借用 L0–L4 的分级思路（本项目自评口径，非官方定义）：

| 级别 | 含义 | 本项目 |
|---|---|---|
| **L0** | 只有想法 | — |
| **L1** | 有代码，跑不起来 | — |
| **L2** | 能跑，能演示主流程 | **← 我们在这里** |
| **L3** | 能复现，别人接手能继续做 | 部分达到（有文档、有 Mock 开关、有 README） |
| **L4** | 能交付，有测试、有监控、有运维 | 未达到（无测试、无部署、无监控） |

**为什么是 L2 而不是 L3：**

L3 要求"别人接手能继续做"。我们有 README 和 6 篇文档，这部分达到了；但缺三样：

1. **没有版本控制历史**（这个仓库是后来补的 `git init`，之前的历史丢了）
2. **种子数据三处不一致的风险没解决**
3. **没有一行自动化测试**，改完只能靠手点

**离 L4 差什么：**

- 云函数真实部署 + 端到端联调
- 至少覆盖核心流程的接口测试
- 日志和错误监控
- 数据备份与恢复方案

这个自评不是自谦，是**让别人能准确判断该不该用这个项目**。

## 7. 20 分钟快速验收（给评审者）

如果你想快速判断这个项目，按这个顺序走：

| 时间 | 做什么 | 看什么 |
|---|---|---|
| 0–3 min | `cd uniapp && npm i && npm run dev:mp-weixin` | 能不能编译成功 |
| 3–6 min | 微信开发者工具导入 `dist/dev/mp-weixin` | 首页能不能渲染 |
| 6–10 min | 走一遍：选套餐 → 选场地 → 下单 → 支付 | 闭环通不通 |
| 10–13 min | 订单详情 → 改期 / 退款 | 状态机对不对 |
| 13–16 min | `cd web && npm i && npm run dev`，登录 `admin` | 后台能不能进 |
| 16–19 min | 看 `#/points`、`#/coupon`、`#/feed` | 扩展功能在不在 |
| 19–20 min | 读 [04 · AI 协作复盘](04-ai-playbook.md) 的案例三 | 判断这个团队是不是真的理解自己的代码 |

最后一步是这份仓库真正想被检验的地方。
